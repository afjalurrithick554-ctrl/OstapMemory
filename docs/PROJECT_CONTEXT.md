# OstapMemory — Ядро и контекст проекта

Этот документ — единая, структурированная память проекта OstapMemory. Здесь собрана вся концепция, архитектура, законы логики и текущий вектор развития, очищенные от ежедневной рутины и разрозненных логов.

## 🎯 1. Концепция продукта (Vision)
**OstapMemory** — это универсальный модуль долгосрочной памяти для AI-агентов (OpenCode, OpenCloud, AntiGravity и др.), который одновременно является визуальным инструментом управления проектами для пользователя. 
Продукт решает проблему «потери контекста» у агентов: агенту не нужно заново объяснять задачу, он имеет постоянный доступ к актуальному состоянию проекта через базу данных, которая для пользователя выглядит как интуитивно понятный интерфейс управления (Sheet).

*Примечание: Использование термина "канбан-доска" (или "Канбан") в проекте строго запрещено на уровне архитектуры и общения с агентами.*

## 🛠 2. Утвержденный стек технологий
- **База данных:** `SQLite` + ORM (Prisma или Drizzle). Архитектура позволяет быстрый переход на PostgreSQL.
- **Бэкенд (MCP Сервер):** `Node.js (TypeScript)` + `Express` (сетевой транспорт `SSE` на порту 3001).
- **Интерфейс (Frontend):** `Vue 3` + `Vanilla CSS` (Vite, порт 5173).
- **Интеграция с агентами:** `MCP Server (Model Context Protocol)`.
- **Доставка:** `Docker Compose` (изолированные микросервисы frontend и backend).

## 🏗 3. Архитектура и Механика (Ядро системы)

### 3.1. БД как Истина
Утверждена важнейшая парадигма: **Колонка (Status) ≠ физическое место**.
Пространство — это лишь визуальное представление базы данных. Перемещение карточки — это исключительно изменение значения в ячейке `state` (состояние) конкретной строки в БД. Для агента физического расположения не существует, он видит только строки в БД, что делает его работу безошибочной.

### 3.2. Иерархия и Терминология (Метафора Книги)
Мы полностью отказались от стандартных IT-терминов (проект, доска, задача). Фундаментальная метафора архитектуры: **База данных = Книга**, а элементы внутри — это её страницы и записи.
1. **Space (Пространство / Страница)** — высший уровень изоляции. Аналог **страницы (листа)** в книге. Создание Space — это вклеивание новой пустой страницы. Удаление Space каскадно уничтожает страницу и все записи на ней.
2. **Sheet (Колонки / Разметка)** — логическая структура (разметка) на конкретной странице `Space`.
3. **Card (Карточка / Запись)** — базовая сущность. Это блок контента, жестко привязанный к конкретной странице (`spaceId`).
Внутри карточек поддерживается деление: Epic (Эпик), Subtask (Подзадача), Task (Атомарная Карточка).

### 3.3. Модель данных (Поля карточки)
Каждая карточка содержит жесткий набор полей:
- **Обязательные при создании:** `id`, `title`, `type` (Epic/Subtask/Task), `state` (Текущий статус).
- **Обязательные для старта работы:** `description`, `checklist` (критерии приемки), `assignee`, `deadline`.

### 3.4. Визуальное и логическое разделение карточки
В интерфейсе просмотра карточки жестко разделены:
- **Пользовательское описание:** редактируемое описание от человека.
- **Секция отчетов (AgentReports):** системная изолированная зона, куда пишет ТОЛЬКО агент (через API). Защищена от смешивания с пользовательским текстом. Любая другая модификация агентом запрещена (агент работает строго в режиме "Чтение", кроме специально отведенных зон).

## ⚙️ 4. Жизненный цикл и правила переходов (State-машина)
Разработана строгая система переходов между состояниями (статусами) карточки:

1. **[Этап 1: Идея] (Рождение)** — достаточно только названия.
2. **[Идея ➡️ Готово к работе] (⚡ Автоматика)** — происходит автоматически, как только заполнены все поля: description, checklist, assignee, deadline. Запрет на старт "сырых" карточек.
3. **[Готово к работе ➡️ В процессе] (✋ Ручное управление)** — осознанное взятие в работу исполнителем (человеком или агентом).
4. **[В процессе ➡️ Можно проверять] (✅ Тумблер / Hard Block)** — физически заблокировано, пока не прожаты все пункты `checklist` и не закрыты подзадачи. По достижении условия появляется тумблер перевода на ревью.
5. **[Можно проверять ➡️ Завершено] (👨‍💻 Человек)** — исключительная зона контроля человека. При успехе карточка закрывается. При откате — возвращается "В процессе" с обязательным комментарием.
6. **[Завершено ➡️ Архив] (🕒 Таймер)** — автоматическое перемещение в архив спустя 1 неделю.

## 🏷 5. Система тегов (Управление ИИ)
Теги служат жесткими инструкциями для управления поведением агента (метаданные).
- **Управление ИИ:** `Автопилот`, `Совместно`, `Требует ревью`, `Блок / Ждет`.
- **Контекст:** `Архитектура`, `Баг`, `Фича`, `Рефакторинг`.
- **Приоритет:** `Срочно`.

## 🟢 6. Текущее состояние (Status)
- **База Данных (SQLite + Prisma):** Успешно интегрирована база данных `SQLite` в бэкенд с использованием `Prisma ORM`. Настроено использование Driver Adapters (`better-sqlite3`) для поддержки Prisma 7. Создана модель `Space`. Реализованы REST API эндпоинты (`GET /api/spaces`, `POST /api/spaces`, `DELETE /api/spaces/:id`) для чтения, записи и удаления данных.
- **Интерактив (Space):** Создано и интегрировано модальное окно добавления нового `Space`. Фронтенд успешно сохраняет данные в БД и реактивно обновляет боковое меню без использования мок-данных. Реализовано **Контекстное меню** (вызываемое по правому клику) в сайдбаре для безвозвратного удаления выбранного Space. 
- **Мобильный интерфейс:** Для удобной навигации на мобильных устройствах добавлено выпадающее меню (Dropdown) в шапке (Header), позволяющее переключаться между проектами и быстро создавать новые.
- **Docker-инфраструктура:** Проект полностью разделен на два работающих и взаимодействующих сервиса: `frontend` (5173) и `backend` (3001).
- **Backend (MCP Server):** Успешно запущен MCP-сервер с поддержкой SSE-транспорта. Сервер отдает агентам **Иммутабельные правила** подключения (запрет модификаций, только чтение, изоляция логов, запрет запрещенных слов).
- **Frontend (UI-компоненты):** Успешно произведен рефакторинг терминологии интерфейса (теперь используются термины `Space` и `Card`). Настроено переключение тем (светлая/темная) и адаптивная мобильная версия.
- **Режим Разработчика (Dev Mode):** В шапке реализован тумблер "Dev Mode". При включении клик по любому элементу собирает его точный абсолютный CSS-селектор и позволяет пользователю оставить комментарий. Фронтенд отправляет данные через `POST /api/feedback`, а бэкенд аккуратно сохраняет фидбек в файл `UI_FEEDBACK.md` как чек-лист для выполнения ИИ-агентом. Отработана успешная схема взаимодействия по фидбеку пользователя из UI!
