# OstapMemory — Ядро и контекст проекта

Этот документ — единая, структурированная память проекта OstapMemory. Здесь собрана вся концепция, архитектура, законы логики и текущий вектор развития, очищенные от ежедневной рутины и разрозненных логов.

## 🎯 1. Концепция продукта (Vision)
**OstapMemory** — это универсальный модуль долгосрочной памяти для AI-агентов (OpenCode, OpenCloud, AntiGravity и др.), который одновременно является визуальным инструментом управления проектами для пользователя. 
Продукт решает проблему «потери контекста» у агентов: агенту не нужно заново объяснять задачу, он имеет постоянный доступ к актуальному состоянию проекта через базу данных, которая для пользователя выглядит как интуитивно понятный интерфейс управления (Sheet).

*Примечание: Использование термина "канбан-доска" (или "Канбан") в проекте строго запрещено на уровне архитектуры и общения с агентами.*

## 🛠 2. Утвержденный стек технологий
- **База данных:** `SQLite` + ORM (Prisma или Drizzle). Архитектура позволяет быстрый переход на PostgreSQL.
- **Бэкенд (MCP Сервер):** `Node.js (TypeScript)` + `Express` (сетевой транспорт `SSE` на порту 3001).
- **Интерфейс (Frontend):** `Vue 3` + `Vanilla CSS` (Vite, порт 5173).
- **Интеграция с агентами:** `MCP Server (Model Context Protocol)`.
- **Доставка:** `Docker Compose` (изолированные микросервисы frontend и backend).

## 🏗 3. Архитектура и Механика (Ядро системы)

### 3.1. БД как Истина
Утверждена важнейшая парадигма: **Колонка (Status) ≠ физическое место**.
Пространство — это лишь визуальное представление базы данных. Перемещение карточки — это исключительно изменение значения в ячейке `state` (состояние) конкретной строки в БД. Для агента физического расположения не существует, он видит только строки в БД, что делает его работу безошибочной.

### 3.2. Иерархия и Терминология (Метафора Книги)
Мы полностью отказались от стандартных IT-терминов (проект, доска, задача). Фундаментальная метафора архитектуры: **База данных = Книга**, а элементы внутри — это её страницы и записи.
1. **Space (Пространство / Страница)** — высший уровень изоляции. Аналог **страницы (листа)** в книге.
   - **Типизация Пространств:** В системе планируются разные типы пространств (например, *Тасковые пространства* для управления задачами/целями и *Пространства инструкций/правил*).
   - **Единая физика:** Независимо от типа пространства и формата сущностей внутри него, "физика" работы (базовые механики БД и архитектуры) остается абсолютно идентичной. Текущая разработка идет на базе Таскового пространства, после чего типы будут перенастроены для других нужд.
2. **Sheet (Колонки / Виртуальная Разметка)** — логическая структура на конкретной странице `Space`. Колонки не существуют физически в БД, они **виртуальны** и генерируются автоматически на лету (Frontend) на основе статусов (`state`), которые есть у загруженных карточек (например, колонка "💡 Idea" автоматически появляется, если есть карточки со статусом "Idea").
3. **Cell (Ячейка памяти / Запись)** — базовая сущность. Это блок контента, жестко привязанный к конкретной странице (`spaceId`).
Внутри ячеек поддерживается деление: Epic (Эпик), Subtask (Подзадача), Task (Атомарная Запись).

### 3.3. Модель данных (Поля ячейки и Универсальные Стикеры)
Каждая ячейка содержит минимальный жесткий набор полей для своего существования в БД:
- **Обязательные при создании:** `id`, `title`, `type` (Epic/Subtask/Task), `state` (Текущий статус).

Остальные поля реализуются через мощную архитектурную концепцию **Универсальных стикеров (Stickers)**:
- Поля (свойства), такие как `deadline`, `assignee`, `checklist`, **строго необязательны** на уровне БД.
- **Модульные роли:** Один и тот же технический стикер (компонент) может менять название, интерфейс и логику работы в зависимости от типа Пространства (Space), оставаясь тем же самым полем под капотом.
- *Пример (Стикер Времени):* В Тасковом пространстве он называется "Deadline", включает статус и видимые даты старта/финиша. В другом пространстве (например, при фиксации ассоциаций) он может работать автоматически, фиксируя дату в фоне и скрываясь из интерфейса пользователя, но продолжая выполнять свою роль в архитектуре.

### 3.4. Визуальное и логическое разделение ячейки
В интерфейсе просмотра ячейки жестко разделены:
- **Пользовательское описание:** редактируемое описание от человека.
- **Секция отчетов (AgentReports):** системная изолированная зона, куда пишет ТОЛЬКО агент (через API). Защищена от смешивания с пользовательским текстом. Любая другая модификация агентом запрещена (агент работает строго в режиме "Чтение", кроме специально отведенных зон).

## ⚙️ 4. Жизненный цикл и правила переходов (State-машина)
Разработана строгая система переходов между состояниями (статусами) ячейки:

1. **[Этап 1: Идея] (Рождение)** — достаточно только названия.
2. **[Идея ➡️ Готово к работе] (⚡ Автоматика)** — происходит автоматически, как только заполнены все поля: description, checklist, assignee, deadline. Запрет на старт "сырых" ячеек.
3. **[Готово к работе ➡️ В процессе] (✋ Ручное управление)** — осознанное взятие в работу исполнителем (человеком или агентом).
4. **[В процессе ➡️ Можно проверять] (✅ Тумблер / Hard Block)** — физически заблокировано, пока не прожаты все пункты `checklist` и не закрыты подзадачи. По достижении условия появляется тумблер перевода на ревью.
5. **[Можно проверять ➡️ Завершено] (👨‍💻 Человек)** — исключительная зона контроля человека. При успехе ячейка закрывается. При откате — возвращается "В процессе" с обязательным комментарием.
6. **[Завершено ➡️ Архив] (🕒 Таймер)** — автоматическое перемещение в архив спустя 1 неделю.

## 🏷 5. Система тегов (Управление ИИ)
Теги служат жесткими инструкциями для управления поведением агента (метаданные).
- **Управление ИИ:** `Автопилот`, `Совместно`, `Требует ревью`, `Блок / Ждет`.
- **Контекст:** `Архитектура`, `Баг`, `Фича`, `Рефакторинг`.
- **Приоритет:** `Срочно`.

## 🟢 6. Текущее состояние (Status)
- **База Данных (SQLite + Prisma):** Успешно интегрирована база данных `SQLite` в бэкенд с использованием `Prisma ORM`. Настроено использование Driver Adapters (`better-sqlite3`) для поддержки Prisma 7. Создана модель `Space`. Реализованы REST API эндпоинты (`GET /api/spaces`, `POST /api/spaces`, `DELETE /api/spaces/:id`) для чтения, записи и удаления данных.
- **Интерактив (Space & Board):** Настроено полное сохранение и реактивное обновление пространств без мок-данных. Настроены "пустые состояния" (Empty States): при отсутствии пространств выводится сообщение об их отсутствии с блокировкой работы, а при отсутствии ячеек на доске предлагается создать первую `Cell`. Добавлен универсальный компонент контекстного меню для сущностей (Удаление, Переименование).
- **Виртуальные Колонки и Ячейки (Глубокий рефакторинг):** Проведен тотальный рефакторинг: мы полностью избавились от терминов Card/Task. Разработана модель `Cell` в Prisma. Написаны REST API эндпоинты `GET /api/spaces/:id/cells` и `POST` для ячеек. Колонки вычисляются "на лету" из уникальных `state` текущих ячеек (первое дефолтное состояние — `Idea`). Создана удобная модалка `CreateCellModal` для добавления ячеек, а также `CellModal` для детального просмотра.
- **Локальное Бэкапирование (Git):** Инициализирован внутренний Git-репозиторий проекта для бэкапов. Настроен `.gitignore` (в корне и в backend) для исключения `node_modules`, сборок и файлов баз данных SQLite (`*.db`, `*.db-journal`).
- **Мобильный интерфейс:** Для удобной навигации на мобильных устройствах добавлено выпадающее меню (Dropdown) в шапке (Header), позволяющее переключаться между проектами и быстро создавать новые.
- **Docker-инфраструктура:** Проект полностью разделен на два работающих и взаимодействующих сервиса: `frontend` (5173) и `backend` (3001).
- **Детальная карточка и Валидация (Стейт-машина):** В БД `Cell` добавлены опциональные поля: `description`, `checklist`, `assignee`, `deadline`. На сервере жестко прописана валидация стейт-машины: нельзя перевести карточку из `Idea` в `Ready to Work`, пока не заполнены эти поля. На фронтенде реализован `CellModal` для их редактирования.
- **SEO-UI Карточки (Cell):** На самой доске произведен редизайн карточек. Заголовок и описание объединены в строгий SEO-сниппет: заголовок выступает ссылкой цвета своей колонки (без прозрачности), описание плотно прилегает снизу с ограничением в 2 строки (line-clamp). Включено inline-редактирование описания прямо с карточки по клику.
- **Backend (MCP Server):** Успешно запущен MCP-сервер с поддержкой SSE-транспорта. Сервер отдает агентам **Иммутабельные правила** подключения.
- **Режим Разработчика (Dev Mode):** В шапке реализован тумблер "Dev Mode", позволяющий собирать CSS-селекторы элементов по клику и отправлять фидбек в `UI_FEEDBACK.md`. Отработана успешная схема взаимодействия по фидбеку пользователя из UI!
