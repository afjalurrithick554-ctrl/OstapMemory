# Проектирование структуры доски OstapMemory (TES1-65)

Этот план описывает архитектуру связи базы данных (БД) и визуального интерфейса (Канбан-доски).

## 1. Базовая концепция (БД vs UI)
- **Доска** — это визуальное представление базы данных.
- **Задача** — это одна строка (Row) в таблице `Tasks`.
- **Колонка канбана ≠ физическое место**. Это визуализация свойства `state` (состояние) строки. 
- *Важное уточнение:* Названия состояний (Идея, В процессе и т.д.) — это лишь базовая конфигурация (Default). В будущем пользователь сможет называть их как угодно ("Срочно", "Не срочно"). Движок (физика переходов) будет работать с любыми названиями.

## 2. Типы сущностей (Card Types)
В базе данных существует отдельная колонка `type`, определяющая иерархию задачи:
1. **Epic (Эпик)** — крупная сущность-контейнер. Выступает родителем для других задач.
2. **Subtask (Подзадача)** — задача, у которой есть родитель (Epic или другая Subtask). Поддерживается неограниченная вложенность (матрешка).
3. **Task (Задача)** — атомарная, самостоятельная единица работы. У нее **нет** родителей и **нет** подзадач. (Примечание: баги и прочее оформляются просто как Task).

## 3. Модель данных (Таблица `Tasks`)

| Поле БД | Назначение | Обязательность для создания | Обязательность для работы |
| :--- | :--- | :--- | :--- |
| **`id`** | Уникальный идентификатор | ✅ Да | ✅ Да |
| **`title`** | Название | ✅ Да | ✅ Да |
| **`type`** | Тип (Epic, Task, Subtask) | ✅ Да | ✅ Да |
| **`state`** | Текущее состояние (колонка) | ✅ Да (по умолч. 1-й этап) | ✅ Да |
| **`description`** | Описание задачи | ❌ Нет | ✅ Да |
| **`checklist`** | Критерии приемки | ❌ Нет | ✅ Да |
| **`assignee`** | Исполнитель | ❌ Нет | ✅ Да |
| **`deadline`** | Срок выполнения | ❌ Нет | ✅ Да |

## 4. Жизненный цикл и правила переходов (Transitions)

1. **[Этап 1: Идея] (Создание)**
   - Достаточно заполнить название. Скрипт присваивает `id`.

2. **[Этап 1] ➡️ [Этап 2: Готово к работе] (⚡ АВТОМАТИЧЕСКИЙ ПЕРЕХОД)**
   - Срабатывает сам, как только в БД заполнены ВСЕ поля: `title`, `description`, `checklist`, `assignee`, `deadline`.

3. **[Этап 2] ➡️ [Этап 3: В процессе] (✋ РУЧНОЙ ПЕРЕХОД)**
   - Только физическое перетаскивание или прямая команда человека агенту. Никогда не автоматически.

4. **[Этап 3] ➡️ [Этап 4: Можно проверять] (✅ ТУМБЛЕР «ВЫПОЛНЕНО»)**
   - **Условие (Hard Block):** Переход возможен, только если отмечены ВСЕ пункты чек-листа и завершены ВСЕ подзадачи (если они есть).
   - Пока условия не выполнены, тумблера «Выполнено» нет.
   - Как только всё выполнено, появляется тумблер. Исполнитель нажимает его, и задача перелетает в «Можно проверять». Галочка с тумблера при этом сбрасывается.

5. **[Этап 4] ➡️ [Этап 5: Завершено] (👨‍💻 ТОЛЬКО ЧЕЛОВЕК)**
   - Эту колонку всегда проверяет человек.
   - Если успешна: человек нажимает тумблер «Выполнено» еще раз, и задача отправляется в «Завершено».
   - **Возврат на доработку:** Если найдена ошибка, человек физически перетаскивает карточку назад (или нажимает возврат). Обязательное условие: в задаче должен быть оставлен **комментарий с причиной возврата**.

6. **[Этап 5] ➡️ [Этап 6: Архив] (🕒 ПО ТАЙМЕРУ - 1 Неделя)**
   - Задача находится на доске перед глазами 7 дней, после чего автоматически убирается в архив (состояние обновляется на `Архив`).
