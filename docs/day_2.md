# OstapMemory: Отчет о работе (День 2)

## Основной фокус дня
Сегодня мы полностью спроектировали **внутреннюю физику и логику работы канбан-доски** в рамках задачи `TES1-65: Проектирование структуры доски (Колонки и Карточки)`. Главная цель дня заключалась в том, чтобы убрать любую двусмысленность между визуальным интерфейсом и базой данных, сделав систему прозрачной и защищенной от "галлюцинаций" ИИ-агентов.

---

## 1. Концептуальный прорыв: БД как Истина
Мы утвердили важнейшую парадигму: **Колонка канбана ≠ физическое место**.
Доска — это лишь визуальное представление базы данных. Перемещение карточки по доске — это исключительно изменение значения в ячейке `state` (состояние) конкретной строки в БД. 
Для агента доски не существует, он видит только строки в БД, что делает его работу точной и безошибочной.

*Примечание:* Базовые названия состояний (Идея, Готово, В работе) — это лишь значения по умолчанию. Движок спроектирован так, чтобы работать с любыми пользовательскими названиями, опираясь только на порядковый этап.

## 2. Иерархия и типы сущностей (Card Types)
В БД добавлена колонка `type`, определяющая уровень сущности. Мы отказались от лишних типов (например, `Bug` интегрирован в логику обычных задач).
Утверждены 3 типа:
1. **Epic (Эпик)** — крупная сущность-контейнер, родитель для других задач.
2. **Subtask (Подзадача)** — задача, имеющая родителя. Поддерживается неограниченная вложенность.
3. **Task (Задача)** — атомарная единица работы без подзадач и родителей.

## 3. Модель данных (Обязательные поля `Tasks`)
Каждая карточка (строка БД) имеет жесткий набор полей. Некоторые обязательны при создании, другие — для старта работы.

| Поле БД | Описание | Обязательность |
| :--- | :--- | :--- |
| **`id`** | Уникальный идентификатор | При создании |
| **`title`** | Название карточки | При создании |
| **`type`** | Тип сущности (Epic/Subtask/Task) | При создании |
| **`state`** | Этап жизненного цикла (Колонка) | При создании |
| **`description`** | Подробное описание | Для начала работы |
| **`checklist`** | Критерии приемки | Для начала работы |
| **`assignee`** | Исполнитель задачи | Для начала работы |
| **`deadline`** | Крайний срок | Для начала работы |

На UI-карточке отображаются только `id`, `title`, аватар `assignee` и дата `deadline`.

## 4. Жизненный цикл и правила переходов (Transitions)
Разработана строгая state-машина для продвижения карточек:

1. **[Этап 1: Идея] (Рождение)**
   - Достаточно названия. Остальные поля пустые. 
2. **[Этап 1 ➡️ Этап 2: Готово к работе] (⚡ АВТОМАТИКА)**
   - Как только у задачи заполняются ВСЕ недостающие поля (description, checklist, assignee, deadline), она **автоматически** перепрыгивает в колонку готовности. Запрет на старт "сырых" задач.
3. **[Этап 2 ➡️ Этап 3: В процессе] (✋ РУЧНОЕ УПРАВЛЕНИЕ)**
   - Никогда не происходит автоматически. Исполнитель (человек или агент по команде) должен осознанно взять задачу в работу.
4. **[Этап 3 ➡️ Этап 4: Можно проверять] (✅ ТУМБЛЕР)**
   - **Hard Block:** Физическая невозможность перехода, пока не прожаты все элементы `checklist` и не закрыты все подзадачи.
   - Как только условие выполнено, появляется тумблер «Выполнено». Исполнитель переключает его, и задача уходит на ревью.
5. **[Этап 4 ➡️ Этап 5: Завершено] (👨‍💻 ЧЕЛОВЕК)**
   - Исключительная зона контроля человека. 
   - При успехе: повторное нажатие тумблера закрывает задачу.
   - При откате: физический возврат карточки на этап 3 с обязательным внесением комментария-причины.
6. **[Этап 5 ➡️ Этап 6: Архив] (🕒 ТАЙМЕР)**
   - Автоматическое перемещение закрытой задачи в базу архива ровно через **1 неделю** нахождения на доске.
